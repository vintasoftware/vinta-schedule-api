# GraphQL Aggregations — Implementation Plan

## 1. Goals

1. Partner integrations can group any of four entity families by one or more dimensions and read type-appropriate aggregates over them — `sum` / `avg` / `min` / `max` on numeric fields, `concat` / `min` / `max` on string fields, `min` / `max` on temporal fields, and `count` on every group.
2. Time-series questions ("events per day", "available windows per week") are answered by grouping on a temporal dimension with a `DAY` / `WEEK` / `MONTH` granularity, bucketed in a caller-supplied IANA timezone.
3. Callers can filter *after* aggregation with a typed HAVING input, order groups by a metric, and take the top N.
4. Running totals and moving averages are available through real SQL window functions (`OVER (PARTITION BY … ORDER BY … ROWS BETWEEN …)`).
5. Every aggregate executes as SQL generated by the Django ORM. No raw SQL, no database-defined code, and no post-processing of result rows in Python.

**Non-goals:**

- **No raw SQL of any kind.** This plan does not add `vw_*` views, Postgres functions, procedures or triggers, and so never touches [common/raw_sql_migration_managers.py](../common/raw_sql_migration_managers.py). The [create-postgres-view](../ai-tools/skills/create-postgres-view/SKILL.md) and [create-postgres-function](../ai-tools/skills/create-postgres-function/SKILL.md) skills are out of scope by construction.
- **No Python-side aggregation, reshaping, or gap-filling.** Rows come back from the database already grouped and already aggregated. A resolver may map a row dict onto a Strawberry type; it may not sum, sort, bucket, or synthesise one.
- **No dense time series.** Buckets are sparse: a day with no matching rows produces no row. Zero-filling is the client's job.
- **No REST equivalent.** This is a public GraphQL surface only. The internal REST API gains nothing here.
- **No aggregation over `OrganizationMembership`, `WebhookEvent`, `ExternalEventChangeRequest`, `BookingPolicy`, or billing models.** Four entity families only.
- **No cross-entity joins in one aggregate.** `calendarEventAggregate` groups events; it cannot simultaneously aggregate blocked times. Two queries, two fields.
- **No percentile, median, stddev, or ordered-set aggregates** in v1.
- **No materialised or pre-computed rollups.** Every aggregate is computed live against the base tables.
- **No new feature-flag framework.** See **Guiding Decisions**.

## 2. Guiding Decisions

| Decision | Resolution |
|---|---|
| **Type-appropriate operations are enforced by the schema, not the resolver** | Each aggregatable model field becomes a GraphQL field whose type is `NumericAggregate`, `StringAggregate`, `DateTimeAggregate` or `BooleanAggregate`. `title { sum }` is then not a runtime error — it fails GraphQL validation before a resolver runs or a connection is taken. The alternative (a `[{op, field}]` metric list) cannot express "strings are not summable" in the type system at all, and gives partner codegen nothing to work with. |
| **Aggregate fields require the same resource scope as the entity's list field** | `calendarEventAggregate` requires `PublicAPIResources.CALENDAR_EVENT` — the scope that already lets the caller page the same rows one at a time. An aggregate therefore discloses nothing new, which is what keeps `MIN(title)` and `concat(description)` from being a back-door read. Dedicated `*_ANALYTICS` resources were rejected for the opposite reason: they would be a *new* grant path over the same PHI-bearing columns. |
| **No feature flag; per-token resource grants are the rollout control** | The repo has no flag framework — no waffle, no flags module, nothing in settings — and the surface here is purely additive (new root fields, new optional fields on existing types, new input and output types; no existing resolver changes shape). A system user without the entity's resource already cannot reach the field, so enabling one partner, soaking, then widening is already expressible. Building a flag framework to serve one additive feature is a larger change than the feature. Consequence: **this plan has no flag-removal phase**, by justification rather than omission. |
| **Bucketing uses a caller-supplied IANA timezone** | `CalendarEvent` and friends store `start_time_tz_unaware` (naive local) plus a per-row `timezone` column, with `start_time` a `GeneratedField` computed by `convert_naive_utc_to_timezone`. "Per day" is therefore genuinely ambiguous. The caller passes an IANA name and the ORM applies `TruncDay("start_time", tzinfo=ZoneInfo(tz))`, giving one consistent wall clock across a multi-region organization. The rejected alternative — bucketing on each row's own local day via `start_time_tz_unaware` — is cheaper and needs no timezone argument, but silently mixes wall clocks inside a single result set. |
| **Filter inputs are objects, diverging from the surrounding style** | Every existing list field (`calendarEvents`, `blockedTimes`, …) filters through flat scalar keyword arguments. Aggregates take `filter: CalendarEventFilterInput` instead. The divergence is deliberate: an aggregate field already carries `groupBy`, `having`, `orderBy`, `window`, `timezone`, `limit` and `offset`, and flattening the filter predicates alongside those produces a signature nobody can read. It is a known inconsistency, recorded in **Open Questions** with a migration path for the list fields. |
| **Buckets are sparse** | Generating a dense date series without raw SQL needs either a date-dimension table (a schema change on a HIPAA-scoped database, plus a backfill and a horizon someone must extend) or a Python fill loop (which is the post-processing this plan forbids). Sparse is the only option consistent with both constraints, and the client already owns the date axis it is rendering. |
| **Window functions ride in the same statement as the aggregation** ⟵ *superseded during Phase 6; the original decision is kept below* | The decision as planned read: "applied over a subquery, not beside the aggregation … the grouped queryset is wrapped and the window applied on the outside", on the reasoning that Django computes `Window` expressions after grouping and refuses to filter on one. Phase 6 found the wrapping unnecessary. Postgres evaluates `OVER` after `GROUP BY` and after `HAVING`, so a running total over grouped rows *is* `SUM(COUNT("id")) OVER (…)` at one query level. Django only refuses to build that through `Sum(Count(...))`, which is a guard on `Aggregate`, not on the SQL: a `Func` subclass carrying `window_compatible` says the same thing and is accepted. What the ORM genuinely does refuse — filtering on a window, and Django's own habit of adding a window annotation to the `GROUP BY` — is handled by `GroupedWindow.get_group_by_cols` returning nothing, which is true rather than a workaround, since a window is computed after grouping and can never be a grouping key. The shipped construction keeps `HAVING`, every `OVER` clause and `LIMIT` in **one** statement instead of two nested ones, so a top-N page carries a running total over the whole result rather than over the page. Still entirely ORM-generated SQL, and still the single largest technical risk in the plan, which is why windows get their own phase. See the module docstring of [public_api/aggregations/executor.py](../public_api/aggregations/executor.py). |
| **Nested aggregates fold the parent key into the GROUP BY** | Aggregates are reachable under any parent, including list fields. Resolved naively that is one grouped query per parent row with no batching path — `DjangoOptimizerExtension` batches `select_related`/`prefetch_related`, not `GROUP BY`. Instead, sibling aggregates at one level are collected and executed as a single grouped query whose `GROUP BY` includes the parent key, then dispatched back to parents. This is real work rather than a cap, and it is the deepest phase in the graph. |
| **Cost is bounded at four independent points** | A mandatory bounded date range on every aggregate field (precedent: `MAX_CODE_GATED_RANGE`), `limit` capped at 100 through the existing `_slice_qs`, a per-query statement timeout, and the nested-batching guarantee above. Any one of them alone leaves a hole: a date range does not bound group cardinality, a limit does not bound scan cost, and a timeout only converts a slow query into a failed one. |
| **Every aggregate query's shape is audit-logged; no values ever are** | Actor, organization, entity, group-by dimensions, metric names, filter bounds and returned row count go to the existing `audit_service` via `actor_from_system_user`. Field *values* — titles, descriptions, attendee identifiers — are never logged, so the audit trail does not itself become a PHI store. Identifiers in the log are opaque ids. |
| **Counts are `Count("id")`, and multi-relation counts use `Subquery`** | Combining several `Count()` calls over different relations in one `annotate()` fans out the join and double-counts. [public_api/queries.py:1314-1341](../public_api/queries.py#L1314-L1341) already solves this for `childOrganizations` with `Subquery`-wrapped per-relation counts; the aggregation engine reuses that shape rather than rediscovering the bug. |
| **Tenant scoping comes from the managers, never from the aggregate layer** | Aggregate querysets start from the model's default `OrganizationScopedManager` and the existing `public_api/scoping.py` helpers (`scoped_calendar_ids`, `scoped_appointment_type_queryset`, `scoped_calendar_pool_queryset`). The aggregation engine never calls `original_manager` or `unscoped()`. A `GROUP BY` over an unscoped queryset would silently aggregate across tenants — the one bug in this feature that would not look like a bug in its output. |

## 3. Data Model Changes

No new models, no new columns, no migrations for the aggregation feature itself. Aggregation reads existing tables.

### 3.1 New constant — `AuditAction.AGGREGATE_QUERY`

Added to the existing `TextChoices` in [audit_integration/constants.py](../audit_integration/constants.py) so aggregate reads are a first-class audited action rather than a generic access log line.

### 3.2 Type plumbing — `public_api/aggregations/`

A new package. No Django models; these are dataclasses and Strawberry types shared by every entity.

```python
# public_api/aggregations/plan.py
@dataclass(frozen=True)
class MetricSpec:
    """One requested aggregate: the model field, the operation, and the alias
    the row dict will carry it under."""
    alias: str
    field_path: str          # ORM path, e.g. "duration_minutes"
    op: AggregateOp          # SUM | AVG | MIN | MAX | COUNT | CONCAT
    options: Mapping[str, Any] = field(default_factory=dict)  # separator, distinct


@dataclass(frozen=True)
class DimensionSpec:
    """One GROUP BY dimension. `granularity` is set only for temporal fields."""
    alias: str
    field_path: str
    granularity: TemporalGranularity | None = None
    tzinfo: ZoneInfo | None = None


@dataclass(frozen=True)
class AggregateQueryPlan:
    """The fully resolved request, built from the GraphQL selection before any
    ORM call. This is what the audit hook records and what the executor turns
    into a queryset — the seam that keeps audit independent of execution."""
    entity: AggregatableEntity
    dimensions: tuple[DimensionSpec, ...]
    metrics: tuple[MetricSpec, ...]
    filter_bounds: FilterBounds
    having: HavingSpec | None
    order_by: tuple[OrderSpec, ...]
    window: WindowSpec | None
    limit: int
    offset: int
```

Field-kind to aggregate-type mapping lives in `public_api/aggregations/registry.py` and is the single place that decides which operations a model field exposes.

## 4. API Design

### 4.1 Shared aggregate types

```graphql
type NumericAggregate {
  sum: Float
  avg: Float
  min: Float
  max: Float
}

type StringAggregate {
  "Postgres string_agg. Ordered by the group's ordering for determinism."
  concat(separator: String = ",", distinct: Boolean = false): String
  min: String
  max: String
}

type DateTimeAggregate {
  min: DateTime
  max: DateTime
}

type BooleanAggregate {
  "Count of rows where the field is true."
  trueCount: Int!
  falseCount: Int!
}

enum TemporalGranularity { DAY WEEK MONTH }
```

### 4.2 Per-entity aggregate fields

Six root fields, one per aggregatable entity family:

| Field | Resource required | Grouped model |
|---|---|---|
| `calendarEventAggregate` | `CALENDAR_EVENT` | `CalendarEvent` |
| `availableTimeAggregate` | `AVAILABLE_TIME` | `AvailableTime` |
| `blockedTimeAggregate` | `BLOCKED_TIME` | `BlockedTime` |
| `appointmentTypeAggregate` | `APPOINTMENT_TYPE` | `AppointmentType` |
| `calendarAggregate` | `CALENDAR` | `Calendar` |
| `calendarPoolAggregate` | `CALENDAR_POOL` | `CalendarPool` |

Shape, using `CalendarEvent` as the worked example:

```graphql
calendarEventAggregate(
  filter: CalendarEventAggregateFilterInput!   # start/end datetime REQUIRED
  groupBy: [CalendarEventGroupByInput!]!
  timezone: String!                            # IANA name, e.g. "America/Sao_Paulo"
  having: CalendarEventHavingInput
  orderBy: [CalendarEventAggregateOrderInput!]
  window: WindowInput
  limit: Int = 100
  offset: Int = 0
): [CalendarEventAggregateRow!]!

input CalendarEventGroupByInput {
  field: CalendarEventGroupByField!             # CALENDAR_ID | APPOINTMENT_TYPE_ID | START_TIME | ...
  granularity: TemporalGranularity              # temporal fields only; null otherwise
}

type CalendarEventAggregateRow {
  key: CalendarEventGroupKey!
  count: Int!
  durationMinutes: NumericAggregate
  title: StringAggregate
  description: StringAggregate
  startTime: DateTimeAggregate
  isBundlePrimary: BooleanAggregate
}

type CalendarEventGroupKey {
  "Every groupable dimension, nullable; only those named in groupBy are populated."
  calendarId: Int
  appointmentTypeId: Int
  startTime: DateTime
}
```

### 4.3 HAVING and metric ordering

```graphql
input CalendarEventHavingInput {
  count: IntComparison
  durationMinutes: NumericAggregateComparison
  and: [CalendarEventHavingInput!]
  or: [CalendarEventHavingInput!]
}

input NumericAggregateComparison {
  sum: FloatComparison
  avg: FloatComparison
  min: FloatComparison
  max: FloatComparison
}

input FloatComparison { eq: Float  gt: Float  gte: Float  lt: Float  lte: Float }

input CalendarEventAggregateOrderInput {
  "Order by a group key dimension, or by a metric — exactly one must be set."
  key: CalendarEventGroupByField
  metric: CalendarEventMetricRef
  direction: OrderDirection = DESC
}
```

`having` becomes `.annotate(...).filter(...)` on the annotation, which Django renders as `HAVING`. `orderBy` on a metric becomes `.order_by()` on the annotation alias.

### 4.4 Window functions

```graphql
input WindowInput {
  partitionBy: [String!]           # group key aliases
  orderBy: [WindowOrderInput!]!
  frame: WindowFrameInput
}

input WindowFrameInput {
  type: WindowFrameType = ROWS     # ROWS | RANGE
  start: WindowBound = UNBOUNDED_PRECEDING
  end: WindowBound = CURRENT_ROW
}

enum WindowBound { UNBOUNDED_PRECEDING PRECEDING CURRENT_ROW FOLLOWING UNBOUNDED_FOLLOWING }
```

Window metrics appear on the row type as a separate sub-selection so they are distinguishable from plain aggregates:

```graphql
type CalendarEventAggregateRow {
  # ... aggregates as above
  window: CalendarEventWindowMetrics
}

type CalendarEventWindowMetrics {
  runningCount: Int
  runningDurationMinutes: Float
  movingAvgDurationMinutes: Float
  rank: Int
  percentOfTotal: Float
}
```

### 4.5 Errors

| Condition | Response |
|---|---|
| `filter.startDatetime` / `endDatetime` absent | GraphQL validation error — they are non-null on the input type. |
| Range exceeds the configured maximum span | `GraphQLError("Date range exceeds the maximum of N days")`. |
| `limit` outside 1–100 | `GraphQLError("Limit must be between 1 and 100")` — reuses `_slice_qs`. |
| `timezone` not a valid IANA name | `GraphQLError("Unknown timezone")`. Never echoes the input back. |
| `granularity` set on a non-temporal dimension | GraphQL validation error via a separate non-temporal group-by input variant. |
| Statement timeout hit | `GraphQLError("Aggregate query exceeded its time budget")`, no plan details disclosed. |
| Missing resource scope | Existing `OrganizationResourceAccess` message, unchanged. |

## 5. Phased Rollout

### Crew

| Agent | Role | Tier | Takes | Why this tier |
|---|---|---|---|---|
| `tier4` | implementer | 4 | Phase 0, Phase 6, Phase 7 | The generic metric/dimension engine, the window-over-subquery construction, and the batched nested `GROUP BY`. All three are novel here — no precedent in this repo, and each fails in ways a test suite does not obviously catch. |
| `tier3` | implementer | 3 | Phase 2, Phase 3, Phase 4 | Multi-file orchestration over an engine that already exists: bucketing, wiring six root fields with their permissions and guards, and the HAVING/order layer. Established patterns, non-trivial branching. |
| `tier2` | implementer | 2 | Phase 1, Phase 5 | Filter input types mirroring existing filter arguments, and an audit hook that consumes a plan object somebody else built. Pattern application against a fixed interface. |
| `reviewer` | reviewer | 4 | — reviews every phase | Must sit at or above Phase 7, the hardest phase on the plan; a reviewer below it could never be picked for it. One reviewer covers the range. |

Three implementers for a graph never wider than two. `tier4` is there because Phases 0, 6 and 7 cannot be handed down. `tier3` and `tier2` are there for cheapness — without them the Tier 2 and Tier 3 phases would run on Opus — and they supply the concurrency in waves 1 and 4. A fourth implementer would add neither.

Tier-to-model ids come from [resources/ai-models.yaml](../ai-tools/skills/plan-feature/resources/ai-models.yaml), whose `last_verified` is 2026-07-13 — about two months old at time of writing. Worth a glance before the run.

### Execution graph

Wave = how deep a phase sits in the dependency graph. Phases in the same wave have no dependency on each other and are implemented concurrently.

| Wave | Phases | Agent | Depends on |
|---|---|---|---|
| 1 | Phase 0, Phase 1 | `tier4`, `tier2` | — |
| 2 | Phase 2 | `tier3` | Phase 0, Phase 1 |
| 3 | Phase 3 | `tier3` | Phase 2 |
| 4 | Phase 4, Phase 5 | `tier3`, `tier2` | Phase 3 |
| 5 | Phase 6 | `tier4` | Phase 4 |
| 6 | Phase 7 | `tier4` | Phase 6 |

**File overlap:** Phase 0 and Phase 1 both create files under `public_api/aggregations/` but never the same one, and both export from its `__init__.py` — trivial merge. Phase 4 and Phase 5 are the pair worth watching: Phase 4 edits the executor's annotate/filter construction, Phase 5 adds an audit call at the resolver entry point. They meet only at a single registration line in `public_api/aggregations/fields.py`. That seam is why Phase 0 defines `AggregateQueryPlan` as a standalone dataclass — the audit hook consumes the plan, not the executor, so the two phases do not compete over execution logic.

**Idle:** this plan is mostly a chain, and that is the direct cost of splitting by capability rather than by entity. `tier4` is idle through waves 2, 3 and 4; `tier3` and `tier2` are idle through waves 5 and 6; `tier2` is also idle in waves 2 and 3. Only waves 1 and 4 run two-wide. Splitting by entity instead would have put four phases in one wave, at the price of every capability landing four times — the trade was made deliberately, and this note is what it looks like at run time.

### Phase 0 — Aggregate engine: metric + dimension primitives

**Goal**: ship the entity-agnostic machinery that turns a GraphQL selection into an ORM-executable aggregate plan. No user-visible surface on its own — this is the foundation every later phase consumes, and it exists separately because six entities wiring the same engine independently is how the engine ends up with six subtly different behaviours.

**Depends on**: nothing — starts from the base branch.

**Feature flag**: none — see **Guiding Decisions**; the surface is purely additive and gated by existing per-token resource grants.

Changes:
1. `@public_api/aggregations/__init__.py`, `plan.py`: the `MetricSpec` / `DimensionSpec` / `AggregateQueryPlan` dataclasses from **Data Model Changes**.
2. `@public_api/aggregations/types.py`: `NumericAggregate`, `StringAggregate`, `DateTimeAggregate`, `BooleanAggregate` Strawberry types, plus `TemporalGranularity`.
3. `@public_api/aggregations/registry.py`: the model-field-kind to aggregate-type mapping, and the per-entity registry of which fields are groupable and which are aggregatable. One place decides that `title` gets `StringAggregate` and never `NumericAggregate`.
4. `@public_api/aggregations/executor.py`: turns an `AggregateQueryPlan` into `.values(...).annotate(...)` against a caller-supplied base queryset. Counts use `Count("id")`; multi-relation counts use the `Subquery` shape from [public_api/queries.py:1314-1341](../public_api/queries.py#L1314-L1341). Never touches `original_manager` or `unscoped()`.
5. `@public_api/aggregations/errors.py`: the error messages from **API Design → Errors**, so no phase invents its own wording.

Spec use-case: shared scaffolding — no use-case yet.

Tests:
- **Unit**: `@public_api/tests/aggregations/test_registry.py` — every aggregatable field on all six entities maps to exactly one aggregate type; a numeric field never exposes `concat`; an unknown field path raises rather than silently returning no metric.
- **Unit**: `@public_api/tests/aggregations/test_plan.py` — plan construction is deterministic and frozen; alias collisions between a dimension and a metric are rejected.
- **Integration**: `@public_api/tests/aggregations/test_executor.py` — against real rows, asserts the generated queryset produces one row per distinct key with correct `sum`/`avg`/`min`/`max`/`count`; asserts a multi-relation count does **not** double-count under join fan-out (build two related rows per parent and assert the exact count); asserts the executor's SQL contains `GROUP BY` and that `len(connection.queries)` is 1.

**Assigned to**: `tier4` (Tier 4) — an entity-agnostic aggregation engine with no precedent in this repo, and the piece every later phase is built on. A wrong abstraction here is paid for six times.

**Reusable skills**: `write-unit-test`.

Acceptance: `AggregateQueryPlan` can be built and executed against `CalendarEvent` in a test, returning correctly grouped and aggregated rows in a single query, with no GraphQL surface exposed yet.

### Phase 1 — Per-entity aggregate filter inputs

**Goal**: give each of the six entities a typed filter input that narrows its queryset before aggregation, with the bounded date range made mandatory at the type level.

**Depends on**: nothing — starts from the base branch. Filter inputs constrain a queryset and never reference a metric or a dimension, so they are independent of the engine.

**Feature flag**: none — purely additive input types, unreferenced until Phase 3.

Changes:
1. `@public_api/aggregations/filters.py`: `CalendarEventAggregateFilterInput`, `AvailableTimeAggregateFilterInput`, `BlockedTimeAggregateFilterInput`, `AppointmentTypeAggregateFilterInput`, `CalendarAggregateFilterInput`, `CalendarPoolAggregateFilterInput`. Temporal entities carry non-null `startDatetime` / `endDatetime`.
2. Each input exposes an `apply(queryset)` that returns a narrowed queryset, starting from the model's scoped manager. Reuses [public_api/scoping.py](../public_api/scoping.py) helpers — `scoped_calendar_ids`, `scoped_appointment_type_queryset`, `scoped_calendar_pool_queryset` — rather than re-deriving owner scope.
3. Maximum-span validation against a new `MAX_AGGREGATE_RANGE` constant in [public_api/constants.py](../public_api/constants.py), mirroring the existing `MAX_CODE_GATED_RANGE` precedent.
4. Export from `public_api/aggregations/__init__.py`.

Spec use-case: shared scaffolding — no use-case yet.

Tests:
- **Unit**: `@public_api/tests/aggregations/test_filters.py` — a range exceeding `MAX_AGGREGATE_RANGE` raises the exact documented message; absent bounds fail at the type level.
- **Integration**: `@public_api/tests/aggregations/test_filter_scoping.py` — a scoped system user's filter never returns rows outside its calendar scope; asserts the queryset a filter produces is still organization-scoped by building rows in two organizations and asserting the second tenant's rows are absent.

**Assigned to**: `tier2` (Tier 2) — six input types following one shape, against filter predicates that already exist as keyword arguments on the corresponding list fields. Exact precedent to mirror.

**Reusable skills**: `write-unit-test`.

Acceptance: each of the six filter inputs narrows its model's scoped queryset correctly and rejects an over-long date range, verified by tests; nothing is reachable from the schema yet.

### Phase 2 — Group-by dimensions and temporal bucketing

**Goal**: let a plan group by scalar dimensions and by a temporal dimension at `DAY` / `WEEK` / `MONTH` granularity in a caller-supplied IANA timezone — the half of the feature that answers "events per day".

**Depends on**: Phase 0 (the `DimensionSpec` dataclass and the executor's `.values(...)` construction this extends), Phase 1 (the filter inputs that bound the queryset a grouped query runs over — bucketing an unbounded range is exactly the query this plan is built to prevent).

**Feature flag**: none — purely additive.

Changes:
1. `@public_api/aggregations/dimensions.py`: per-entity group-by field enums (`CalendarEventGroupByField`, …) and the `GroupByInput` variants — a temporal variant carrying `granularity`, a scalar variant without it, so `granularity` on a non-temporal field is a validation error rather than a runtime one.
2. Extend `public_api/aggregations/executor.py`: temporal dimensions become `TruncDay` / `TruncWeek` / `TruncMonth` over `start_time` with `tzinfo=ZoneInfo(tz)`. Scalar dimensions pass through to `.values()`.
3. `@public_api/aggregations/timezone.py`: IANA name validation, raising the documented error without echoing the input.
4. Per-entity `*GroupKey` output types, every dimension nullable, populated only for dimensions the query named.

Spec use-case: shared scaffolding — no use-case yet.

Tests:
- **Unit**: `@public_api/tests/aggregations/test_dimensions.py` — an unknown IANA name raises; the enum rejects a field that is not groupable.
- **Integration**: `@public_api/tests/aggregations/test_bucketing.py` — the load-bearing test. Events either side of a local midnight in `America/Sao_Paulo` land in different `DAY` buckets, and the *same* events bucketed in `UTC` land in the same one. Asserts a `WEEK` bucket boundary. Asserts a sparse result: a range covering a day with no events returns no row for it, rather than a zero.
- **Integration**: `@public_api/tests/aggregations/test_multi_dimension.py` — grouping by `[START_TIME:DAY, CALENDAR_ID]` produces the cross-product of non-empty combinations only, in one query.

**Assigned to**: `tier3` (Tier 3) — multi-file work over an existing engine, with the genuinely subtle part being timezone-correct bucketing against a `GeneratedField`. Established ORM patterns, non-trivial branching.

**Reusable skills**: `write-unit-test`.

Acceptance: a plan grouping `CalendarEvent` by day in a named timezone returns one row per non-empty local day with correct counts, in a single query, verified against a DST boundary.

### Phase 3 — Aggregate root fields, permissions, and cost guards

**Goal**: expose all six aggregate fields on the public GraphQL schema, correctly scoped and bounded. This is the phase that makes the feature reachable by a partner.

**Depends on**: Phase 2 (the group-by dimensions, `*GroupKey` types and temporal bucketing every field exposes — a field without dimensions is not an aggregate).

**Feature flag**: none — new root fields, gated by existing per-token resource grants.

Changes:
1. `@public_api/aggregations/fields.py`: a factory building one `strawberry_django.field` per entity from the registry, so six fields share one resolver body. Each carries `permission_classes=[IsAuthenticated, OrganizationResourceAccess]`.
2. [public_api/queries.py](../public_api/queries.py): register the six fields on `Query`.
3. [public_api/permissions.py](../public_api/permissions.py): six entries in `FIELD_TO_RESOURCE_MAPPING`, each mapping to the **same** resource as the entity's existing list field per the table in **API Design**.
4. Per-entity `*AggregateRow` output types with `count` plus one field per aggregatable model field, typed from the registry.
5. Cost guards: `limit` through the existing `_slice_qs` (1–100), the mandatory bounded range from Phase 1, a deterministic `ORDER BY` on the group key so paging is stable, and a per-query statement timeout applied around aggregate execution only.

Spec use-case: shared scaffolding — no use-case yet.

Tests:
- **Unit**: `@public_api/tests/aggregations/test_field_registration.py` — all six fields appear in the schema; every one has an entry in `FIELD_TO_RESOURCE_MAPPING` (a loop over the registry asserting no field was added without its resource).
- **Integration**: `@public_api/tests/aggregations/test_aggregate_permissions.py` — a token **without** `CALENDAR_EVENT` gets the standard permission error from `calendarEventAggregate`; a token with it succeeds; a token scoped to calendar A sees no aggregate contribution from calendar B's events. The cross-tenant case asserts an empty result rather than another tenant's numbers.
- **Integration**: `@public_api/tests/aggregations/test_cost_guards.py` — `limit` of 0 and 101 both raise the documented message; an over-long range raises; a query without bounds fails validation.
- **Integration**: `@public_api/tests/aggregations/test_aggregate_queries.py` — end-to-end through the schema for all six entities: `calendarEventAggregate` grouped by calendar returns correct `count` and `durationMinutes { sum avg }`; `title { concat(separator: "; ") }` returns the concatenated titles; asserts the whole document executes in one database query.

**Assigned to**: `tier3` (Tier 3) — six fields, their permission mappings and their guards, orchestrated across the schema, permissions and constants modules. The risk is coverage and correctness of wiring rather than novelty.

**Reusable skills**: `create-graphql-public-query`, `write-unit-test`.

Acceptance: a partner token with `CALENDAR_EVENT` scope can run `calendarEventAggregate` grouped by day and by calendar and get correct counts and numeric rollups; a token without that scope is refused; `limit` above 100 and an unbounded range are both rejected.

### Phase 4 — HAVING, metric ordering, and top-N

**Goal**: let callers filter groups on their aggregated values, order by a metric, and take the top N — turning "all calendars with their counts" into "the ten busiest calendars".

**Depends on**: Phase 3 (the six registered aggregate fields and their `*AggregateRow` types, which this phase adds `having` and `orderBy` arguments to).

**Feature flag**: none — new optional arguments on fields that already exist; omitting them preserves Phase 3 behaviour exactly.

Changes:
1. `@public_api/aggregations/having.py`: `IntComparison`, `FloatComparison`, `NumericAggregateComparison` and per-entity `*HavingInput` with `and` / `or` composition.
2. Extend `public_api/aggregations/executor.py`: `having` becomes `.filter()` applied **after** `.annotate()`, which Django renders as `HAVING`. Guards that a `having` clause referencing an unrequested metric still annotates it rather than erroring.
3. `@public_api/aggregations/ordering.py`: per-entity `*AggregateOrderInput` accepting either a key dimension or a metric reference, with a validation that exactly one is set. Ordering by a metric becomes `.order_by()` on the annotation alias, with the group key appended as a tiebreak so paging stays deterministic.
4. Add `having` and `orderBy` arguments in `public_api/aggregations/fields.py`.

Spec use-case: shared scaffolding — no use-case yet.

Tests:
- **Unit**: `@public_api/tests/aggregations/test_having.py` — an order input with both `key` and `metric`, or neither, is rejected; `and`/`or` nest correctly.
- **Integration**: `@public_api/tests/aggregations/test_having_execution.py` — `having: {count: {gt: 2}}` drops groups of 1 and 2 and keeps a group of 3, and the emitted SQL contains `HAVING` rather than the filtering happening in Python (assert the queryset returns the filtered count directly, and that one query ran).
- **Integration**: `@public_api/tests/aggregations/test_metric_ordering.py` — ordering by `count` descending with `limit: 3` returns exactly the three busiest calendars in the right order; ties break deterministically across repeated runs.
- **Integration**: a regression case in `test_aggregate_queries.py` asserting a query with neither `having` nor `orderBy` returns byte-identical results to Phase 3.

**Assigned to**: `tier3` (Tier 3) — annotation-aware filtering and ordering across six entities, where the subtlety is which clause lands in `WHERE` versus `HAVING`. Same engine, established patterns.

**Reusable skills**: `write-unit-test`.

Acceptance: `calendarEventAggregate(having: {count: {gt: 20}}, orderBy: [{metric: COUNT, direction: DESC}], limit: 10)` returns at most the ten busiest calendars with more than 20 events, computed entirely in SQL.

### Phase 5 — Audit logging for aggregate queries

**Goal**: record who ran which aggregate over what, so PHI-bearing rollups have an access trail — without the log itself holding any field values.

**Depends on**: Phase 3 (the registered aggregate fields whose resolver entry point this hooks, and the `AggregateQueryPlan` those resolvers build).

**Feature flag**: none — additive logging on existing fields; no response shape changes.

Changes:
1. [audit_integration/constants.py](../audit_integration/constants.py): add `AGGREGATE_QUERY` to the `AuditAction` choices.
2. `@public_api/aggregations/audit.py`: a hook taking an `AggregateQueryPlan` plus the returned row count and writing one audit record via the DI-provided `audit_service`, using `actor_from_system_user` for the public API's system user and `scope_from_organization_id` for the tenant.
3. Record **only**: actor identity snapshot, organization, entity name, dimension field paths and granularities, metric aliases and operations, filter bounds (the datetime range and any scalar id predicates), requested limit/offset, and the returned row count. Explicitly **not** recorded: any aggregated value, any group key value, any concatenated string. Filter predicate values are recorded as opaque record ids only, never as free text.
4. One registration line in `public_api/aggregations/fields.py` wiring the hook into the shared resolver.

Spec use-case: shared scaffolding — no use-case yet.

Tests:
- **Unit**: `@public_api/tests/aggregations/test_audit_payload.py` — the load-bearing test. Builds a plan whose metrics include `title { concat }` and whose filter names a calendar, runs the hook, and asserts the serialized audit payload contains the metric *alias* and *operation* but **no** title value, no concatenated string and no free-text predicate. Asserts against the whole payload, not a substring check.
- **Integration**: `@public_api/tests/aggregations/test_audit_integration.py` — running `calendarEventAggregate` through the schema writes exactly one audit record with action `AGGREGATE_QUERY`, the right actor and organization, and the correct row count; a query that returns zero rows still writes a record.

**Assigned to**: `tier2` (Tier 2) — consuming a plan object that Phase 0 defined through an audit service that already exists, with `actor_from_system_user` as exact precedent. The discipline is in what the test asserts is *absent*, which the test spells out.

**Reusable skills**: `write-unit-test`.

Acceptance: every aggregate query writes one `AGGREGATE_QUERY` audit record naming the actor, organization, entity, dimensions, metrics and row count, and a test proves no field value reaches the audit payload.

### Phase 6 — SQL window functions over grouped results

**Goal**: running totals, moving averages, rank and percent-of-total over an already-grouped result — computed by Postgres window functions, not by Python.

**Depends on**: Phase 4 (the `HAVING` and metric-ordering construction this wraps — a window is applied over the grouped, filtered, ordered result, so building it before that layer exists would mean rebuilding it after).

**Feature flag**: none — a new optional `window` argument; omitting it leaves every existing query unchanged.

Changes:
1. `@public_api/aggregations/windows.py`: `WindowInput`, `WindowOrderInput`, `WindowFrameInput`, the `WindowBound` / `WindowFrameType` enums, and per-entity `*WindowMetrics` output types.
2. Extend `public_api/aggregations/executor.py` with the construction from **Guiding Decisions**: annotate `Window(expression=..., partition_by=..., order_by=..., frame=RowRange(...))` onto the grouped queryset, in the same statement as the aggregation. *(As planned this read "wrap the grouped queryset and apply the window on the outside"; the subquery wrapping turned out to be unnecessary — see the superseded row in **Guiding Decisions** for why, and for what replaces it.)* Entirely ORM-generated; no raw SQL.
3. Validation: `partitionBy` may name only aliases that appear in `groupBy`; a `window` without `orderBy` is rejected, because an unordered running total is meaningless rather than merely wrong.
4. Add the `window` argument and the `window` sub-selection in `public_api/aggregations/fields.py`.

Spec use-case: shared scaffolding — no use-case yet.

Tests:
- **Unit**: `@public_api/tests/aggregations/test_window_validation.py` — `partitionBy` naming a dimension absent from `groupBy` is rejected; a window without `orderBy` is rejected.
- **Integration**: `@public_api/tests/aggregations/test_window_execution.py` — events across five days produce a running count that is monotonically non-decreasing and whose final value equals the plain total; a moving average over a 3-row frame matches a hand-computed expectation asserted as literal values; `percentOfTotal` sums to 100 across the partition. Asserts one query, and asserts the SQL contains `OVER (` so a Python fallback cannot pass this test.
- **Integration**: `partitionBy: [CALENDAR_ID]` keeps each calendar's running total independent — two calendars interleaved by date, asserting neither one's total leaks into the other.
- **Integration**: a regression case asserting a query with no `window` argument returns byte-identical results to Phase 4.

**Assigned to**: `tier4` (Tier 4) — the window-over-subquery construction is the plan's largest technical risk: Django's `Window` does not compose with `.values().annotate()` grouping in the obvious way, and the workaround has to stay inside the ORM. Novel, and wrong answers here look plausible.

**Review models**: reviewer Tier 4 — a running total that is subtly wrong (off-by-one frame bound, partition leaking across groups) returns confident numbers that no type check and no smoke test catches, and partners will build reporting on them. The review reads the frame construction against the emitted SQL regardless of the author's tier.

**Reusable skills**: `write-unit-test`.

Acceptance: `calendarEventAggregate` grouped by day with a window partitioned by calendar returns a correct running count and moving average, computed in SQL with an `OVER` clause, in a single query.

### Phase 7 — Nested aggregates with batched GROUP BY

**Goal**: make aggregates usable under any parent type — including list fields — without turning N parent rows into N grouped queries.

**Depends on**: Phase 6 (the final executor shape, including the window subquery wrapping — batching folds a parent key into the `GROUP BY` of whatever query the executor now builds, so doing it before windows exist would mean doing it twice).

**Feature flag**: none — new fields on existing types; every root-level query keeps its Phase 6 behaviour.

Changes:
1. `@public_api/aggregations/nested.py`: a per-level collector that gathers sibling aggregate selections resolving under the same parent list, executes them as **one** grouped query whose `GROUP BY` includes the parent key, and dispatches rows back to the parent objects that asked for them.
2. Add nested aggregate fields to the relevant existing types in [calendar_integration/graphql.py](../calendar_integration/graphql.py) — `CalendarGraphQLType.eventAggregate`, `CalendarGraphQLType.blockedTimeAggregate`, `CalendarPoolGraphQLType.eventAggregate`, `AppointmentTypeGraphQLType.eventAggregate`.
3. Permission inheritance: a nested aggregate requires the **aggregated entity's** resource, not the parent's — nesting an event aggregate under a calendar does not let a calendar-only token read event rollups.
4. Interaction with `DjangoOptimizerExtension`: the collector runs outside the optimizer's `select_related`/`prefetch_related` path and must not defeat it. Documented in the module, asserted by a query-count test.

Spec use-case: shared scaffolding — no use-case yet.

Tests:
- **Unit**: `@public_api/tests/aggregations/test_nested_collection.py` — the collector groups sibling selections correctly and produces one plan per distinct aggregate shape.
- **Integration**: `@public_api/tests/aggregations/test_nested_batching.py` — the load-bearing test. A query over 25 calendars each selecting `eventAggregate` executes a **bounded** number of queries that does not grow with the calendar count: assert the exact query count at 5 calendars and at 25 calendars and assert they are equal. Without batching this test fails with 5 versus 25.
- **Integration**: `@public_api/tests/aggregations/test_nested_permissions.py` — a token with `CALENDAR` but not `CALENDAR_EVENT` is refused the nested `eventAggregate` while still reading the calendar itself.
- **Integration**: nested and root aggregates over the same filter return identical numbers — the batched path and the direct path must not disagree.

**Assigned to**: `tier4` (Tier 4) — batching a `GROUP BY` across a parent level, coexisting with an existing query optimizer, is the hardest piece in the plan and the one with the least precedent anywhere in this repo.

**Review models**: reviewer Tier 4 — the failure mode is a silent N+1 that passes every functional test and only shows up as database load in production, so the review has to read the query-count assertions as carefully as the logic.

**Reusable skills**: `write-unit-test`.

Acceptance: a document selecting `eventAggregate` under a list of 25 calendars runs the same number of queries as the same document over 5 calendars, returns the same numbers as the equivalent root-level aggregate grouped by calendar, and refuses a token lacking the event resource.

## 6. Risk & Rollout Notes

**No feature flag, by justification.** The surface is additive: new root fields, new optional arguments on those fields, new optional fields on existing types, new input and output types. No existing resolver changes shape and no existing response changes. Rollout control is the existing per-system-user resource grant — enable `CALENDAR_EVENT` aggregate access for one partner, soak, then widen. There is consequently no flag-removal phase in this plan. If a kill switch is later wanted independent of token scopes, the cheapest addition is a setting consulted by the field factory in `public_api/aggregations/fields.py`, which is a single chokepoint by design.

**Window functions are the technical risk.** Django computes `Window` expressions after grouping and raises `NotSupportedError` on attempts to filter one. Combining `.values().annotate()` aggregation with `Window` in one queryset does not generally work, so Phase 6 wraps the grouped queryset and applies the window outside it. If that construction turns out not to hold for a particular frame type, the fallback is still ORM — a `Subquery` annotation over the grouped queryset — and **not** raw SQL or Python post-processing. Phase 6 is deliberately late so this risk lands against a working, tested engine rather than an empty one.

**Query cost is the operational risk.** A grouped scan over a large tenant's event history is the most expensive thing this API will be able to do. Four independent guards apply: a mandatory bounded date range, a limit capped at 100, a per-query statement timeout, and Phase 7's batching bound on nested fan-out. The `OrganizationRateLimiter` already in the schema applies on top. Before the first partner is enabled, check the query plans for grouped scans on `CalendarEvent` filtered by `start_time` range plus organization — if `start_time` (a `GeneratedField`) is not index-backed for range predicates, add an index. That index is the one migration this feature may need, and it is additive and concurrent-creatable.

**Locks and migrations.** The only schema change in this plan is the `AuditAction.AGGREGATE_QUERY` choice, which is a Python-level `TextChoices` addition and generates a no-op or trivial migration. If the index above proves necessary, create it `CONCURRENTLY` and follow [add-migration](../ai-tools/skills/add-migration/SKILL.md) for the lock-aware path on a hot table.

**PHI exposure.** Aggregates over `CalendarEvent` can surface `title` and `description` content through `min`, `max` and `concat`. Two properties bound this: the aggregate field requires the same resource scope as the list field, so no caller gains reach they did not already have; and every query's shape is audited. What is deliberately **not** implemented is a k-anonymity floor — a group of size 1 returns that single record's values to a caller who could equally have read the row directly. If a partner is ever granted aggregate access *without* row-level read, that decision changes and a minimum group size becomes mandatory. Recorded in **Open Questions**.

**Rollback.** Every phase is independently revertible: Phases 0–2 add unreferenced modules, Phase 3 adds six root fields whose removal restores the prior schema, Phases 4–6 add optional arguments whose removal restores the prior behaviour, and Phase 7 adds fields to existing types. Reverting Phase 5 stops audit writes without touching the query path. No phase requires a data migration to undo. Beyond code revert, removing the resource grant from a partner's system user disables the surface for that tenant immediately, with no deploy.

**Cross-tenant correctness is the one bug that would not look like one.** A `GROUP BY` over an insufficiently scoped queryset returns plausible numbers that silently include another organization's rows. Phases 1, 3 and 7 each carry a cross-tenant test asserting a second organization's rows contribute nothing.

## 7. Open Questions

| Question | Recommended default | Owner |
|---|---|---|
| Should a minimum group size (k-anonymity) be enforced on string-returning aggregates? | **No for v1** — the same-resource permission rule means the caller could already read the underlying rows, so suppression adds a semantic wrinkle (rollups stop reconciling with lists) without closing a real gap. This flips the moment any partner is granted aggregate access without row-level read. | Security / compliance lead |
| Aggregate fields use filter *input objects* while every existing list field uses flat scalar arguments. Should the list fields migrate to match? | **Not in this plan.** Migrating them is a breaking change to a published partner API and deserves its own deprecation window. Revisit once the aggregate inputs have proven their shape in production. | API owner |
| Is `start_time` index-backed for range predicates on `CalendarEvent`? | Check query plans before enabling the first partner; add a concurrent index if not. Treated as a rollout checklist item rather than a phase, since it may already exist. | Whoever runs the pre-enablement check |
| Should `WEEK` buckets start Monday or Sunday? | **Monday** — Django's `TruncWeek` uses Monday, and matching the ORM default avoids a custom expression. Worth confirming against partner expectations before the contract is published. | API owner |
| Do partners need result sets larger than 100 groups? | **No for v1** — the cap matches every other list field here. If a warehouse consumer needs bulk extraction, that is a different surface (a paged export), not a raised limit on a live query. | API owner |
